# FlowDesk（問い合わせ・案件管理システム）

**問い合わせを一元管理し、対応漏れを防止し、受注につなげる。**

中小企業向けの問い合わせ・案件・タスク管理システムです。電話・メール・フォーム・LINE・紹介など、バラバラに届く問い合わせを1か所に集め、
「誰が・いつまでに・何をするか」を見える化し、対応漏れを自動で知らせます。案件化から受注・売上までをつなげて分析できます。

- 業種を問わず使える汎用設計（問い合わせ経路・種別・案件ステータスと受注確度・タグ・優先度の表示名を設定で変更）
- デモ会社「株式会社NextWorks」（法人向け業務改善・Web制作、社員8名）の約半年分のデータで、ログインなしですぐに体験できます
- 会社・人物・顧客はすべて架空です

## 解決する課題

| よくある状態 | FlowDesk では |
| --- | --- |
| 問い合わせがメール・電話メモ・Excel に散らばり、返信漏れが起きる | すべての経路の問い合わせを1つの一覧に。24時間以上未対応のものを自動で警告 |
| 見積を出したまま追いかけを忘れ、失注する | 見積提出から7日でフォローのアラート。見積提出時にフォローのタスクを自動作成 |
| 案件の状況は担当者に聞かないと分からない | 案件ボード（Kanban）をドラッグで更新。ステータス・確度・受注見込が自動で連動 |
| 月末に Excel で集計して報告資料を作っている | ダッシュボード・分析・日次〜年間のレポートを自動で集計。CSV にも出力 |
| どの集客経路が売上につながっているか分からない | 経路ごとに「問い合わせ → 案件化 → 受注 → 受注金額」を並べて比較 |

導入効果の試算（紹介ページに掲載）：管理と報告にかかる時間 **月30時間 → 月10時間（月20時間・年240時間の削減）**。
※ 従業員8名・月20〜30件の問い合わせがある会社を想定した試算で、効果を保証するものではありません。

## 差別化ポイント

1. **対応漏れアラート**（`src/lib/domain/alerts.ts`）
   - 24時間以上未対応の問い合わせ／見積提出から7日経過／最終接触から30日経過の案件／期限超過タスク／今日・期限切れのフォロー予定
   - 日数は設定で変更可能。ダッシュボードの「今日やること」に重要度順で並ぶ
   - アラートは保存せず、表示のたびに現在のデータから計算するので、対応すれば自動で消える
2. **問い合わせ経路の分析**（`/analytics`）
   - 経路別の件数・案件化率・受注率・受注金額・平均受注単価を並べ、「件数は多いが売上にならない経路」「件数は少ないが高単価の経路」が分かる

## DB 設計

```
organizations ─┬─ organization_settings（1:1。業種・タイムゾーン・アラート日数・各種リスト）
               ├─ organization_members（利用者 × 組織 × 役割）── profiles
               ├─ pipeline_stages（分類 open/won/completed/lost/hold・既定確度・ボード列）
               ├─ inquiry_sources（問い合わせ経路）
               ├─ customer_tags ─ customer_tag_relations ─ customers
               ├─ inquiries ──(converted_deal_id)── deals ── deal_stage_history
               ├─ tasks / activities（顧客・問い合わせ・案件に紐づく）
               └─ sales（受注案件ごとの売上。deals のトリガーが同期）
```

- 金額は円の整数（bigint）。受注見込は生成列 `expected_revenue = round(見積金額 × 確度 / 100)`。TypeScript の計算（`src/lib/domain/money.ts`）と一致することをテストで確認
- すべての子表に `(organization_id, 親id)` の複合外部キー。別の組織の顧客・案件を参照できない
- 業務ルールはトリガーで DB に持たせる：連番、ステータス変更時の確度（受注100%・失注0%固定、手動設定は維持）・受注日・履歴・売上の同期、見積提出時のフォロータスク、対応履歴からの初回対応日時・最終接触日・次回予定の反映、案件削除時の問い合わせの差し戻し
- 案件化は関数 `convert_inquiry()` で1トランザクション（顧客作成 → 案件 → 対応履歴・タスクの引き継ぎ → 問い合わせを「案件化」に）

詳しくは [docs/DESIGN.md](docs/DESIGN.md)。マイグレーションは `db/migrations/`。

## マルチテナントと権限（RLS）

- 全業務表に `organization_id`。RLS で「ログイン中の組織」の行だけが見え、書ける（`current_org_id()`）
- アプリは必ず `runAsUser()` を通して DB に接続し、トランザクションの中で `authenticated` ロールと利用者の情報を設定する。RLS を通らない経路はない
- 表への書き込み権限は列単位で許可（番号・作成者・売上・履歴などは書けない）。権限の一覧はテストで固定

| | 管理者 | マネージャー | 一般担当者 |
| --- | --- | --- | --- |
| 問い合わせ | 全件 | 全件 | 自分担当・未割当・自分が受け付けたもの |
| 案件・タスク | 全件 | 全件 | 自分担当・自分が作成したもの |
| 担当者の変更 | ○ | ○ | 自分か未割当のみ |
| 削除 | ○ | ○ | ×（自分の記録・タスクを除く） |
| 分析・売上・レポート・CSV | ○ | ○ | × |
| 設定・メンバー管理 | ○ | × | × |

画面（`requireRole`）・Server Action（Zod と役割の確認）・DB（RLS とトリガー）の3段で守り、DB が最後の砦です。

## ローカルで動かす

PostgreSQL 16 以上が必要です。

```bash
npm install
cp .env.example .env.local        # DATABASE_URL を自分の環境に合わせる
npm run db:local:reset            # DB（flowdesk）を作り直してマイグレーション
npm run db:seed                   # 見本の組織（株式会社NextWorks）を作る
npm run dev                       # http://localhost:3000
```

### デモログイン

- ログイン画面の「管理者として体験」「マネージャーとして体験」「一般担当者として体験」を押すと、あなた専用のデモ組織を作って入ります（24時間で自動削除）
  - 管理者：代表の山田さん（全データ・分析・設定）
  - マネージャー：営業部長の佐藤さん（チームの案件・担当の割り当て・売上予測）
  - 一般担当者：営業の鈴木さん（自分の問い合わせ・案件・タスク）
- 画面上部のバナーで、同じデモ組織のまま役割を切り替えられます
- 見本の組織には `admin@` / `manager@` / `member@flowdesk.example` などでログインできます（パスワードはローカルでは `flowdesk-demo-2026`、公開環境では `SEED_LOGIN_PASSWORD`）

### Seed データ

`src/lib/demo/generator.ts` が「今日」を基準に決まった乱数で作ります（同じ日なら同じデータ）。

社員8名・顧客 約80社・問い合わせ 約170件・案件 約80件・タスク 約240件・対応履歴 約460件・半年分。
未対応の問い合わせ・見積フォロー待ち・長期未接触・期限超過タスク（7件）など、アラートの見どころも含みます。

### 環境変数

| 名前 | 内容 |
| --- | --- |
| `DATABASE_URL` | PostgreSQL の接続文字列（サーバー専用） |
| `DATABASE_URL_UNPOOLED` | マイグレーション用の直接接続（Neon / Supabase。任意） |
| `SEED_LOGIN_PASSWORD` | 見本の組織のパスワード（公開環境では必須・12文字以上） |
| `CRON_SECRET` | 毎日の定期処理の合言葉（公開環境では必須・16文字以上） |
| `DEMO_MAX_ACTIVE` / `DEMO_CREATE_LIMIT_PER_HOUR` | デモの同時数・1時間あたりの作成数の上限（任意） |

## テスト

```bash
npm run lint && npm run typecheck
npm test                          # 単体テスト＋DB テスト（ローカルの PostgreSQL を使う）
npm run test:e2e                  # ブラウザでの E2E（PC とスマートフォンの幅）
```

- 単体（69件）：受注見込金額、0件のときの率、案件化率・受注率、初回対応時間と初回対応率、アラートの条件、日付の境界（月末・年末・日本時間の0時）、タイムゾーン、CSV（囲み・改行・BOM・数式の無害化・取り込みの検証）、入力の検証、デモデータの件数と整合性
- DB（29件）：マルチテナントの分離（他の組織は見えない・書けない・作れない）、役割ごとの見える範囲、担当者変更の制限、案件化、トリガー（初回対応・確度・受注日・売上・見積フォロー・案件削除）、生成列と TypeScript の一致、権限の一覧、データの整合性
- E2E（11件）：問い合わせ登録 → 対応記録 → 案件化 → ボードでドラッグ → タスク完了、役割ごとの権限、CSV、ログインとログアウト、スマートフォンの幅
- GitHub Actions：プルリクエストごとに上の全部を実行（`ci.yml`）。公開したサイトには「公開環境の E2E テスト」（`production-e2e.yml`）を手動で実行

## デプロイ（Vercel + Neon）

1. Vercel でこのリポジトリを読み込み、Storage から Neon を接続する（`DATABASE_URL` が入る）
2. 環境変数 `SEED_LOGIN_PASSWORD`（12文字以上）と `CRON_SECRET`（16文字以上）を設定する
3. デプロイすると、ビルドの途中でマイグレーションと見本の組織の作成が自動で行われる（`scripts/deploy/vercel-build.ts`）
4. 毎朝6時（日本時間）に期限切れのデモの削除と見本の組織の作り直しが動く（`vercel.json` の Cron）

Supabase を使う場合は、Connection pooling（Transaction）の接続文字列を `DATABASE_URL`、Direct を `DATABASE_URL_UNPOOLED` に設定します。
