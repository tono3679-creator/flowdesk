# FlowDesk 設計メモ

実装に入る前に整理した要件・画面・DB・権限・アラート・構成・実装順序です。
実装で変えたところは、このファイルも合わせて直します。

## 1. 要件整理

**一番伝えたい価値**：問い合わせを一元管理し、対応漏れを防ぎ、受注につなげる。

| 区分 | 内容 |
| --- | --- |
| 差別化① 対応漏れ防止 | 24時間以上未対応の問い合わせ／見積提出から7日経過／最終接触から30日経過／期限超過タスク／今日・期限切れのフォロー予定を**自動で検出**し、ダッシュボードの「今日やること」に優先度順で並べる。判定日数は設定で変更 |
| 差別化② 経路分析 | 問い合わせ件数だけでなく「経路 → 案件化 → 受注 → 受注金額」をつなげて、どの経路が売上になっているかを出す |
| 業種への横展開 | 問い合わせ経路・問い合わせ種別・案件種別・案件ステータス（受注確度つき）・顧客タグ・優先度の表示名を設定で変更 |
| マルチテナント | すべての業務表に organization_id。RLS で自社の行だけ。複合外部キー (organization_id, id) で他社の行を参照できない |
| 日本仕様 | 日本語 UI・日本円（整数・3桁カンマ）・YYYY/MM/DD・24時間表記・Asia/Tokyo |

### 用語と計算の定義（src/lib/domain が唯一の実装）

- 受注見込金額 = 見積金額 × 受注確度 ÷ 100（円未満四捨五入。DB の生成列も同じ式）
- 案件化率 = 案件化した問い合わせ ÷ 問い合わせ件数 × 100
- 受注率 = 受注 ÷（受注＋失注）× 100、失注率 = 失注 ÷（受注＋失注）× 100（0件のときは「—」）
- 初回対応時間 = 受付から、その問い合わせに紐づく最初の対応履歴まで。初回対応率 = 設定時間（既定24時間）以内に初回対応した割合
- 平均受注単価 = 受注金額合計 ÷ 受注件数、平均受注期間 = 問い合わせ受付（なければ案件作成）から受注日までの日数
- 「受注」はステータスの分類が won（受注・作業中・完了）、「失注」は lost。期間は受注日・失注日で数える
- 売上 = 売上計上日（受注案件ごとに1件。完了日が入ればその日、なければ受注日）

## 3. DB 設計（db/migrations）

```
organizations ─┬─ organization_settings（1:1。業種・タイムゾーン・アラート日数・各種リスト）
               ├─ organization_members（user × org × role）── profiles（表示名・役職）
               ├─ pipeline_stages（名前・分類 open/won/lost/hold・既定確度・ボード列・並び順）
               ├─ inquiry_sources（問い合わせ経路）
               ├─ customer_tags ─ customer_tag_relations ─ customers
               ├─ inquiries ──(converted_deal_id)── deals ── deal_stage_history
               ├─ tasks（customer / inquiry / deal のどれかに紐づく・任意）
               ├─ activities（customer / inquiry / deal に紐づく対応履歴）
               └─ sales（受注案件ごとの売上計上。deals のトリガーが同期）
```

- 金額は bigint（円）。受注見込は生成列 `expected_revenue = round(estimated_amount * probability / 100)`
- すべての子表に `(organization_id, 親id)` の複合外部キー → 別の会社の顧客・案件を指せない
- 履歴の自動反映（トリガー）：対応履歴を登録すると、顧客・案件の最終接触日、問い合わせの初回対応日時（未対応→対応中）、次回対応日、見積提出日を更新
- ステータス変更：確度を既定値に（手動変更した案件は維持。受注は100%・失注は0%固定）、履歴を記録、受注日・失注日を記録、売上を同期
- index：organization_id を先頭にした検索用、期限・次回対応日、名前の部分一致（pg_trgm）

## 5. アラートロジック（src/lib/domain/alerts.ts）

| 種類 | 条件（既定値は設定で変更） | 重要度 |
| --- | --- | --- |
| 未対応問い合わせ | ステータスが未対応のまま受付から24時間以上 | 緊急・高優先度は critical、それ以外 high |
| 見積フォロー | 見積提出から7日以上、受注・失注・保留になっていない | high |
| 長期未接触 | 進行中の案件で最終接触（なければ作成）から30日以上 | medium |
| タスク期限超過 | 期限が今日より前で未完了 | 優先度に応じて critical / high |
| フォロー予定 | 次回フォロー日（問い合わせ・案件）が今日または過去 | 過去 high／今日 medium |

日付の境界は組織のタイムゾーン（Asia/Tokyo）の暦日で判定する。「今日やること」はアラート＋今日期限のタスクを重要度→経過時間の順に並べる。アラートは保存せず、表示のたびに現在のデータから計算する（解決したら自動で消える。古いアラートが残らない）。

## 6. ディレクトリ構成

```

db/migrations/*.sql         スキーマ → 業務ルール（トリガー）→ RLS・権限 → セッション
scripts/                    migrate / seed / deploy（Vercel ビルド時の DB 構築）
src/app/(public)            紹介ページ・ログイン
src/app/(app)               業務画面
src/app/api                 CSV 出力・定期処理
src/components/{ui,common,layout,…}
src/lib/domain              ★ 計算・判定（純粋関数・テスト対象）：metrics / alerts / dates / money / csv
src/lib/data                DB からの読み取り（RLS 付き）
src/lib/actions             Server Actions（zod で検証 → DB）
src/lib/demo                デモデータ生成（決定的な乱数・「今」基準）
tests/unit · tests/db · tests/e2e
```
